### Forecast evaluation with WAPE (Part 0)
We evaluate the demand model with WAPE, the sum of absolute errors divided by the sum of actual sales. MAPE divides by each day's sales and breaks on zero-sales days, which are common for slow-moving perishables. WAPE also weights errors by volume. On 60 held-out days, the model reached a WAPE of 15.43%, against 25.37% for a naive "same day last week" forecast. When future promotions and holidays are unknown, as in the live API, it reached 17.89%. The offline simulation that replays these days is deterministic: a fixed dataset seed and end date, and a fixed model seed. Two runs produce byte-identical KPI files, which lets us use the simulation as a CI gate.

### Business-KPI deployment gate (Part 1)
Unit tests check whether code does what it says. They cannot tell whether a change makes a store waste more food. Our pipeline therefore replays 60 held-out days with the candidate code and model, and compares the simulated waste rate, fill rate, stockout days and forecast WAPE with reference values from the main branch. Image building and deployment depend on this gate. In our tests, a one-line change that orders a full week of stock at once passed all 113 backend tests, but the gate rejected it because simulated waste rose from 0.27% to 61%. Reducing the model from 300 to 40 trees stayed under the absolute accuracy test, but the gate rejected it because simulated waste rose to 0.40%. The reference values change only through a manual, reviewed workflow. On this synthetic data, our ordering policy performed about the same as a moving-average rule and clearly better than re-ordering what sold (fill rate 99.5% vs 93.1%). The gate therefore requires "no worse than baseline within tolerance", not strict superiority.

### Closed-loop monitoring and retraining (Part 2)
After deployment, the API logs every forecast it serves and scores it when that day's sales are recorded. Prometheus receives the live 7-day WAPE, the forecast bias, and a drift score (the Population Stability Index between the last 28 days of sales and the training data). Alert thresholds were measured before they were chosen. Store-level live error stayed at or below 1.42× the held-out error in normal weeks on three synthetic datasets, while a degraded model or a 40% demand shift reached at least 1.49×. This gives a threshold of 1.45, with a narrow margin. Median PSI stayed at or below 0.134 in normal weeks, and was at least 0.325 after a ±25% shift, which gives a threshold of 0.25. In a live demonstration, injecting a 40% demand shift moved the ratio from 0.86 to 1.58 and the PSI from 0.05 to 0.73, triggering ModelDegraded and DataDrift. A retrain workflow exports the latest sales. It runs data validation, the model check and the business gate, and opens a pull request only if all of them pass. Building this loop exposed three problems that we fixed: partial same-day sales inflated the error, the training-time error was optimistic because future promotions are unknown when serving, and the demo data was shifted by days that were not whole weeks, which broke weekday alignment.

### ML supply-chain security (Part 3)
We treat the training data and the model file as part of the software supply chain. A data validator checks schema, value ranges, duplicates, missing days, row counts and extreme shifts against the previous dataset. It blocked ×10 poisoning, negative quantities, duplicates, a renamed column and a truncated file, while still allowing a genuine 40% demand change. Training writes a manifest with SHA-256 hashes of the data, model and metrics. The API verifies them before unpickling the model and refuses a mismatch, so a tampered model returns 503 on readiness and the rollout fails. Images get an SBOM, a keyless cosign signature tied to our repository's workflow on the main branch, and a signed SBOM attestation. The deploy script verifies both and deploys by digest. All GitHub Actions are pinned to commit SHAs, after a March 2026 incident in which the version tags of a popular scanning action were redirected to malicious code. These checks do not catch subtle poisoning, and the manifest alone cannot stop an attacker who can rewrite both files; the signature covers that case.

### Fault-injection evaluation (Part 4)
To test whether these additions matter, we injected eight realistic faults, plus a control with no fault, into separate branches. Each branch ran through a generic pipeline (lint, unit tests, SonarQube, Trivy with default scanners, image build and scan) and through ours. *[Replace with the GitHub results: for each fault, the stage that caught it and the time to detection, then the detection rate of each pipeline.]* In a local run where only some stages could execute, the generic pipeline caught 2 of 8 faults and ours caught 6 of 8, with no false alarm on the control. The faults the generic pipeline missed were about business outcomes (a policy bug, a degraded model), the data (poisoning) and the deployment configuration (a root, privileged container).

### Access control and hardening (Part 5)
The API now requires a login. Passwords are hashed with Argon2id, and a 30-minute JWT carries one of two roles: viewers can read everything, managers can also change data. Login is rate-limited (5 failures per client and username in 5 minutes). The client address is taken from the entry that our proxy adds, so a forged header cannot bypass the limit. In production, the service refuses to start without its secrets. The web server hides internal endpoints (metrics, API docs) and sends a strict Content-Security-Policy with no inline scripts; a browser test through nginx showed no violations. The pipeline adds Gitleaks over the full git history and frontend unit tests (Vitest), and it makes the SonarQube quality gate mandatory on the main branch. The test suite has 113 backend tests (94% coverage) and 13 frontend tests.
