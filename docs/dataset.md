# Dataset used in FreshTrack

## Summary

| | |
|---|---|
| **Type** | **Synthetic** (generated by our own script). It is not data from a real store. |
| File | `backend/data/sales.csv` |
| Generator | `backend/scripts/generate_sales.py` (seed **42**, **730** days, end date **2026-06-30**) |
| Period | 2024-07-01 to 2026-06-30 (730 days, no gaps) |
| Products | 8 perishable grocery items (dairy, bakery, fruit, vegetables, eggs) |
| Rows | 5,840 (8 products × 730 days), one row per product per day |
| Columns | `date`, `sku`, `quantity` (units sold that day), `on_promo` (0/1), `is_holiday` (0/1) |
| Missing values / duplicates | 0 / 0 |
| SHA-256 | `31ff26600cd73c0809afece880b4064a8ddd69480907ca4961bb638aa47f6901` |
| Profile (used by data validation) | `backend/data/profile.json` |

**Why synthetic:** the project has no access to a real store's sales data. A synthetic dataset lets the project run offline and keeps every experiment exactly repeatable: the same seed always gives the same file, byte for byte. We report every inventory result as *simulated on synthetic data*.

## How it is generated

For each product and each day, the expected demand is:

```
avg_daily_demand
  × weekday factor   (Mon 0.90, Tue 0.85, Wed 0.90, Thu 0.95, Fri 1.05, Sat 1.25, Sun 1.20)
  × yearly cycle     (1 + 0.10 · sin(2π · day / 365 + random phase per product))
  × slow trend       (1 + 0.0002 · day)
  × 1.6 on holidays  (24 days in two years, shared by all products)
  × 1.35 on promotion days (about 6% of days, random per product)
```

The sold quantity is a **Poisson** random draw around that expected demand, which adds realistic day-to-day noise. Product settings come from `backend/app/catalog.py`.

## How the dataset is used

| Use | Data | Detail |
|---|---|---|
| Model training | first 670 days (2024-07-01 → 2026-05-01) | 5,136 rows after the lag features are built |
| Model test (never seen in training) | last **60 days** (2026-05-02 → 2026-06-30) | 480 rows; time-based split, no shuffling |
| Business-KPI simulation and gate | the same 60 held-out days | `scripts/simulate.py`, `scripts/policy_gate.py` |
| Drift reference | last 90 training days per product | stored in the model metrics |
| Data validation reference | the whole file | `data/profile.json` |
| Demo database | the whole file, dates shifted by whole weeks to end yesterday | `app/seed.py` |
| Unit-test fixture | a *second* synthetic dataset: seed **123**, 400 days, 2025-05-27 → 2026-06-30, 3,200 rows | generated inside `tests/conftest.py`, SHA-256 `d8379d19668c37d79d886a3e664b23f0b3f542f0f360ceb93d4d568da2869997` |

## Verify it yourself

Regenerate the file and compare hashes. They must match exactly.

```bash
cd backend
python scripts/generate_sales.py --out regenerated.csv
python -c "import hashlib;print(hashlib.sha256(open('regenerated.csv','rb').read()).hexdigest())"
# Windows PowerShell alternative:  Get-FileHash regenerated.csv -Algorithm SHA256
# expected: 31ff26600cd73c0809afece880b4064a8ddd69480907ca4961bb638aa47f6901
```

Check the committed file and its profile:

```bash
python scripts/validate_data.py data/sales.csv --reference data/profile.json
```

## Limitations

- The data is synthetic, so the patterns are cleaner than real sales. Our ML forecast's advantage over a simple rule may look different on real data.
- `quantity` is units *sold*. On a real stockout day, true demand would be higher than recorded sales. The synthetic data has no stockouts, so it does not show this effect.
- Holidays are random days, not a real Indian festival calendar.

## Using a real dataset instead

Any daily sales file with the columns `date, sku, quantity, on_promo, is_holiday` works. For example, a subset of the public Kaggle "Corporación Favorita Grocery Sales Forecasting" dataset can be used after mapping its columns, then:

1. Put the file at `backend/data/sales.csv` and add its products to `app/catalog.py`.
2. Run `python scripts/validate_data.py data/sales.csv --write-profile data/profile.json`.
3. Run `python scripts/policy_gate.py --write-baseline` to record new reference KPIs, after a reviewed PR.
4. Recalibrate the alert thresholds (ModelDegraded 1.45, DataDrift 0.25), because they were measured on the synthetic data.
